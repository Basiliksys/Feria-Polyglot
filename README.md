# Feria Polyglot — Голосова та рунічна система мов для D&D

Веб-застосунок для ведення партій у D&D (зокрема у світі Ферії), який замінює звичайний голосовий потік Discord на розумну мовну маршрутизацію:

- **Миттєва DSP-тарабарщина без затримок:** гравець, який **не знає** мови, чує розвернуті гранулярні склади з тематичним акустичним фільтром (інтонація, паузи, емоції та тембр зберігаються, але слова неможливо розібрати).
- **Приховування невідомих мов на сервері:** для слухачів, які не знають мову, замість назви показується `❓ Невідома мова`, а в чаті сервер взагалі не передає оригінальний текст — лише детерміновані руни.
- **Атмосферний тембр:** ті, хто **знає** мову, за бажанням чують 100% розбірливий голос із легким тематичним забарвленням (кришталь для Ельфійської, бас/луна для Інфернальної).
- **Механіки D&D:** магічні стани `Comprehend Languages` (розуміє все, та не говорить) і `Tongues` (розуміє та говорить усіма мовами), **Режим Діалогу** в 1 клік, кнопка «Перекласти групі», **Древні Свитки (Handouts)** та **часткова розшифровка (25% / 50% / 100%)**.
- **Конструктор мов Ферії:** створюйте власні мови й шифри з живим налаштуванням DSP-повзунків.

## Швидкий старт на Windows

1. Запустіть файл **`start-feria-voice.bat`**.
2. Оберіть:
   - **`[1]` Локальний запуск** — відкриє `http://localhost:3456` (підходить для тестування на одному ПК, або по локальній мережі / Radmin VPN).
   - **`[2]` Публічний HTTPS-тунель** — автоматично підніме сервер і згенерує захищене `https://...` посилання для гравців через інтернет (браузери вимагають HTTPS для доступу до мікрофона на чужих ПК).
3. На екрані входу:
   - Гравці клікають на картку свого героя (**Аменемхет-Кемі**, **Адріан Морвейн**, **Ліора**, **Джагатай Кара-Буран**). Також можна дати гравцю пряме посилання вигляду `https://.../?char=liora`.
   - Майстер входить за PIN-кодом **`1250`** (для локального запуску можна змінити у `data/campaign-state.json`; на Render задайте змінну `FERIA_DM_PIN`).

## Деплой на Render (основний варіант)

Найшвидший шлях — Blueprint `render.yaml` у корені репозиторію: **New → Blueprint**, виберіть репо, введіть три секрети (`FERIA_DM_PIN`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`) і застосуйте. Blueprint задає один web-інстанс, `npm ci` / `npm start`, healthcheck `/api/health`, `NODE_ENV=production` і відсутність persistent disk. **`FERIA_DM_PIN` обов'язковий у production** — без нього сервер не стартує (інакше працював би публічний PIN `1250` з seed-файлу). Якщо безкоштовні web-інстанси недоступні — замініть `plan: free` на `0.5c-512mb`.

### Налаштування сервісу

- **Runtime:** Node.js 22 (Blueprint фіксує `NODE_VERSION: "22"`); глобальний `fetch` доступний з Node 18.
- **Build Command:** `npm ci`
- **Start Command:** `npm start`
- **Instance Count:** **1**. Реєстр учасників (`clients`) і WebRTC-сигналінг зберігаються у пам'яті процесу; кілька інстансів бачитимуть різні списки гравців. Масштабування потребує окремого pub/sub (не входить у цей етап).
- **Region:** `frankfurt` (Blueprint). Створюйте Upstash Redis у регіоні **Frankfurt / Central Europe (EU)**, щоб мінімізувати затримку записів стану.
- **Healthcheck Path:** `/api/health`
- **Graceful shutdown:** безкоштовний план використовує стандартне вікно Render; `maxShutdownDelaySeconds` підтримується лише на платних планах, тому його немає в Blueprint. Сервер усе одно закриває WS/HTTP і зливає стан при `SIGTERM`.

### Збереження стану (обов'язково)

Render без платної persistent disk перезаписує файлову систему контейнера при кожному рестарті/деплої. Тому стан партії зберігається в **Upstash Redis REST** (безкоштовний tier), а локальний файл використовується лише як кеш/резерв.

1. Створіть базу даних [Upstash Redis](https://upstash.com/) → REST API.
2. Скопіюйте `UPSTASH_REDIS_REST_URL` і `UPSTASH_REDIS_REST_TOKEN` у **Environment** Render-сервісу.
3. За бажанням задайте `STATE_KEY` (за замовчуванням `feria:campaign-state`), щоб розділити кілька партій у одній базі.

Поведінка при старті:
- якщо в Redis є валідний стан → він завантажується;
- якщо Redis порожній/недоступний → використовується локальний кеш, потім `data/campaign-state.json` як **seed** (файл у репозиторії ніколи не перезаписується);
- записи серіалізуються, об'єднуються (~300 мс) і зливаються у Redis при `SIGTERM`; перед фінальним flush сервер закриває WS/HTTP і блокує нові зміни.
- кожен інстанс перед завантаженням захоплює ключ `<STATE_KEY>:owner` і пише в KV, лише будучи активним; при zero-downtime деплої старий інстанс не перезаписує новий знімок.

Змінні оточення:

| Змінна | Обов'язкова | Призначення |
| --- | --- | --- |
| `PORT` | Render задає автоматично | Порт HTTP/WS (локально за замовчуванням `3456`). |
| `HOST` | ні | Явна адреса слухання, наприклад `127.0.0.1` для тестів. |
| `FERIA_DM_PIN` | **рекомендовано** | PIN Майстра. Перекриває значення зі state-файлу; не зберігається в експорті. |
| `UPSTASH_REDIS_REST_URL` | так (для Render) | URL REST-ендпоінту Upstash. |
| `UPSTASH_REDIS_REST_TOKEN` | так (для Render) | Токен REST-ендпоінту. Секрет, не потрапляє в логи. |
| `STATE_KEY` | ні | Ключ Redis для стану партії. |
| `STATE_DIR` / `STATE_PATH` | ні | Шлях локального кешу. У режимі Upstash за замовчуванням `data/runtime-state.json` (seed-файл у репозиторії не перезаписується); без Upstash — `data/campaign-state.json`. |
| `TURN_URL` / `TURN_URLS` | ні | Comma-separated TURN-адреси для прямого WebRTC. Без значення використовується публічний OpenRelay TURN. |
| `TURN_USERNAME` / `TURN_CREDENTIAL` | ні | Креденціали TURN. Для браузера вони все одно видимі в `/api/rtc-config`, тож рекомендується власний TURN із короткоживучими токенами. |
| `STUN_URLS` | ні | Comma-separated STUN-адреси (за замовчуванням Google + Cloudflare). |

### Спостереження та безпека

- `GET /api/health` повертає `status` (`ok` / `degraded`), `storageMode`, `lastSyncAt`, `lastSaveAt`, `lastSaveError`, `pendingSaves`, `clients`, `buildId` та лічильники. При недоступному Upstash або втраті права запису endpoint повертає **503** — Render не визнає такий інстанс здоровим і не пустить його в роботу з поганим токеном.
- Експорт стану — **POST** `/api/export-state` з PIN у тілі (`{"pin":"..."}`); GET вимкнено, відповіді `/api/*` мають `Cache-Control: no-store`.
- Ліміти PIN рахуються за довіреним IP (один proxy-hop Render) і є спільними для HTTP та WS; WS відхиляє browser-з'єднання з чужим `Origin`; ліміти не скидаються при реконнекті. Шепіт перевіряється і для P2P-сигналінгу, і для релею; Майстер чує всі шепоти так само, як бачить їх у чаті. Звичайні повідомлення більше не відправляють порожній `title` — це повернуло чат після помилки `Invalid title`; сервер однак приймає й старі клієнти з `title: ''`.
- Холодний старт безкоштовного Render-сервісу може зайняти 30–60 с: клієнт автоматично повторює запит до `/api/lobby` і WS-підключення з повідомленням «Сервер прокидається...». Після входу втрата WS відновлюється автоматично (експоненційний backoff до 30 с), а стан учасників звіряється за новим `JOIN_SUCCESS`.

### Аудіошлях (Phase 2)

- WebSocket-релей тепер передає **бінарні кадри PCM** (`public/js/audio-protocol.js`) замість base64 у JSON: у 1.5–2 рази менше трафіку, менше навантаження на CPU та GC. Заголовок кадру містить версію, частоту, номер пакета, ідентифікатор відправника й список цілей; сервер перевіряє відправника за сокетом і застосовує шепіт-ізоляцію.
- Захисний релейний тап працює в **AudioWorklet** (`polyglot-relay-tap-processor`) замість застарілого `ScriptProcessorNode`: даунсемпл 48→24 кГц, голосовий гейт з утриманням і transferable Int16-чанки виконуються поза головним потоком.
- Шумодав тепер реально глушить **вихідний потік** (WebRTC і релей), а не лише підсвічує індикатор: адаптивний шумовий поріг із гістерезисом, відсіювання коротких імпульсів за співвідношенням пік/RMS (клавіатура, кліки миші) і утримання 420 мс після мови. `autoGainControl` вимкнено, бо AGC підсилює фон між словами. «Тест голосу» споживає вже відгейтований потік, тому працює однаково в gibberish/atmospheric. Повзунок відповідає шкалі індикатора (`level = rms × 8`), тож 15% — це RMS ≈ 0.019, а не майже нуль.
- Вбудовані мовні пресети переписані під **природніше звучання**: довші grains, мінімальний sub-octave/ring-mod, менше ревербу/хорусу. Дворфійська стала нижчою, але без «стукоту». Оновлення застосовується до збереженої партії автоматично (`dsp-presets.js`), якщо preset не змінювався вручну — кастомні налаштування ГМа лишаються недоторканими.
- «Звук у loop» усунено з двох боків: grain-и більше не читають один і той самий шматок буфера за фіксованим циклом, а вхідні релейні кадри після підтвердженого WebRTC **не відтворюються** — інакше гравець чув би дві копії фрази з затримкою. Заплановані релейні буфери скасовуються при перемиканні на прямий зв’язок; кадри зниклих гравців ігноруються.
- Для сумісності клієнти з `relayProtocol: 1` і старі сервери все ще працюють через JSON/base64; нові клієнти запитують `relayProtocol: 2` і отримують бінарні кадри.
- Важкі DSP-вузли (скремблер, фільтр, хорус, реверб) тепер **спільні для всіх гравців з однаковим режимом/пресетом** (`public/js/dsp-bus-registry.js`): один ланцюг замість одного на гравця. Гучність і mute залишаються індивідуальними (per-peer `sendGain`), а звільнення останнього слухача знищує шину.

### Зв'язок і відновлення (Phase 3)

- Логіка сесії/WebRTC винесена в чистий модуль `public/js/peer-session.js` (тестується в Node): звіряння списку гравців за знімком (`JOIN_SUCCESS` / `STATE_SYNC`), стан транспорту з backoff-повторними спробами ICE і **perfect negotiation** (GLARE-обробка, rollback, відповідь не створює власну пропозицію).
- Свіжість сигналінгу визначається за серверним `fromClientId` (після реконнекту ID новий) і повним скиданням PC/ICE/negotiator на новому `JOIN_SUCCESS` — клієнтський `epoch` більше не порівнюється між гравцями. Асинхронні помилки signaling/медіа не залишаються unhandled.
- Релей — не «липкий» стан: він залишається увімкненим для всіх станів, крім підтвердженого прямого зв'язку (`connected`), тому гравці за NAT не зависають на «Перепідключення...». Вхідні PCM-кадри одразу перемикають транспорт у `relay`, але **не скасовують активну спробу ICE**: без цього безперервна мова щоразу відкладала б backoff і гравець лишався б у ретрансляторі назавжди. Періодичні спроби ICE повертають прямий зв'язок. Зниклі гравці видаляються з UI/аудіо/PC-карт разом із таймерами та чергами ICE.
- Клієнт бере ICE-конфіг з `GET /api/rtc-config`: окрім STUN там завжди є **TURN** (публічний OpenRelay або власний через env). Без TURN гравці за симетричним NAT взагалі не можуть вийти з ретранслятора — самого backoff ICE недостатньо. Конфіг завантажується до входу в кімнату, тому нові `RTCPeerConnection` одразу знають про TURN.
- `SPEAKING_STATE` більше не шлемо кожні 20 мс: зміна стану відправляється одразу, а рівень — не частіше 10 раз/с і лише при зміні ≥0.05. Це прибрало постійне зростання `rejectedMessages` у health (ліміт speaking — 20/с).
- Додано globals-індикатор стану WS у шапці «Голосової зали» (`online / connecting / syncing / reconnecting / offline`), нові стани точок з'єднання та ARIA-підписи кнопок гравців. Гучність/mute більше не застосовуються при кожному ререндері: префи зберігаються в рушії і виживають заміну ланцюга/реконект.
- Усі обіцянки обробників WS та WebRTC мають `catch`; черга ICE обмежена (64 кандидати), застарілі PC-генерації ігнорують пізні колбеки.

### Локальна перевірка перед деплоєм

```bash
npm ci
npm test      # 63 тести: deploy config, security hardening, WS/reconnect/WebRTC-сесія, audio worklet/engine/buses, relay protocol, rules, state-store, validation, Render-style integration
npm start
```

Інтеграційні тести піднімають реальний сервер з емулятором Upstash (локальний HTTP) і перевіряють руни/приховування мов, шепіт, відхилення надлишкових кадрів, POST-експорт, блокування PIN, **відновлення стану після перезапуску**, а також 503 для зламаного KV, Origin-перевірку WS, ізоляцію P2P-шепоту, flush на шляху graceful shutdown, ліміти після реконнекту і захист від перезапису стану старим інстансом.

### Чек-лист викладу (Phase 4)

1. `npm ci && npm test` локально — усі тести мають бути зеленими (зараз 63).
2. Створіть Upstash Redis REST і тримайте URL/токен готовим; PIN не зберігайте в репо.
3. Створіть сервіс із `render.yaml` (або вручну: Node 22, `npm ci`, `npm start`, `/api/health`, **1 інстанс**, без диска) і заповніть `sync: false` змінні в Dashboard.
4. Після першого деплою відкрийте `https://<service>.onrender.com/api/health`: `status: ok`, `storageMode: upstash`, `clients: 0`, `lastSyncAt` не порожній.
5. Увійдіть як GM і як гравець, перевірте голос, релейний fallback та індикатор стану з'єднання. Зробіть change в партії, дочекайтеся `pendingSaves: 0` у health, перезапустіть сервіс і переконайтеся, що стан повернувся з Upstash.
6. Для кастомного домену додайте його в Render (TLS видається автоматично); WS працює через `wss://` на тому саму хості.
7. Оновлення: `git push` → auto-deploy. Клієнти помічають новий `buildId` у `/api/lobby` і повністю перезавантажуються одразу після перемикання трафіку (щоб підхопити нові JS-асети й автоматично перевстановити WebRTC); стан партії повертається з сервера на `JOIN_SUCCESS`. Старий інстанс втрачає право запису й не перезаписує KV, а перед `SIGTERM` закриває WS/HTTP і зливає стан. Відкат — через **Manual Deploy** попереднього коміту в Dashboard.

`render.yaml`, `.gitignore` і наявність усіх browser-асетів перевіряються окремими тестами конфігурації (`test/deployment-config.test.js`) — без нових npm-залежностей.
